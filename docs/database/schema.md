# Схема данных

Полная ER-модель — [architecture/er-model.md](../architecture/er-model.md) (и `er.mmd`,
`er-model.pdf`). Здесь — владение данными и правила.

## Бизнес-модель

```
University ──┐
             ├──► Interaction ──► WorkflowStage
ITProduct  ──┘        │
ITDirection ── ITProduct   ├── Action (задача со сроком)
                           └── Comment
```

`University`, `ITProduct`, `ITDirection` — справочники.
`Interaction` — главная сущность: связка «вуз + продукт», перемещается по этапам.

## Владелец данных

| Домен | Кто пишет | Кто читает |
| --- | --- | --- |
| Справочники (вузы, продукты, направления) | `api.directories`, только `admin` | все модули, отчёты |
| Этапы воркфлоу | `api.stages`, только `admin` | взаимодействия, отчёты |
| Взаимодействия, задачи, комментарии | `api.interactions` | отчёты, уведомления, аудит |
| Аудит | `middleware.audit` | администратор |
| Файлы | `services.file_storage` (S3/MinIO), в БД — ссылки | экспорт, PDF-руководства |

## Правила

1. **Лимит «не более 2 активных взаимодействий у вуза»** проверяется приложением.
   Ограничения схемы нет — это известное ограничение (см. аудит).
2. **Справочники не удаляются физически**, если на них есть ссылки: сначала
   деактивация.
3. **Кириллица в выгрузках** — сквозное требование: Excel-выгрузка проверяется тестом.
4. **Прод — PostgreSQL 16**, локально допустим SQLite; поведение SQLite-only изменений
   не считается достаточным.

## Проверка

- Согласованность моделей и миграций — `make alembic-check`.
- Установка с нуля и повторное применение — `portability.yml` (`alembic-fresh`,
  `alembic-upgrade-path`).
- Восстановление копии — `portability.yml` (`backup-restore`).
